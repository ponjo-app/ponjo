Agent Config

An agent is the CLI that does a buddy's work (Claude Code, Codex, any other), started by a script. Ponjo runs the script and knows nothing else about it.

The contract

An agent is a filter (architecture):
Working folder new and private; holds only copies of the doc and its sidecar, at the doc's path in the project (in doc mode, under their names)
stdin the prompt: who the buddy is and the rules, then, under The situation now:, what changes from run to run: every thread that asks the buddy and it has not answered, each by its id, and, for a buddy watching the doc, what changed since it last looked: the threads another member wrote in, and the lines of the doc. The rules say what any member can do and the etiquette every member keeps (each edit with a comment saying why, comments of a sentence or two in the thread's language, a comment naming another buddy left to it); how a buddy answers is its persona's. It names files only by their paths in the project, never where a run keeps them: the script tells its agent that, if it needs to (see Paths)
PONJO_DOC the doc copy's path
PONJO_COMMENTS the sidecar copy's path
PONJO_PROJECT the project folder, to read only (see Permissions); empty in doc mode
PONJO_BUDDY the buddy's name
PONJO_TRACE a file, out of the working folder, the agent may write its steps to (see Traces)
PONJO_GROUPS a file, out of the working folder, the agent may write its comments' edits to (see Groups)
PONJO_WAKE a file, out of the working folder, the agent may write the lines of the doc that wake it next to (see Wake)
PONJO_ACTIONS a file, out of the working folder, the agent may write the actions outside the doc its comments propose to (see Actions)
PONJO_SETTING_<KEY> each of the agent's settings
stdout anything; kept in the trace, never posted
Exit 0 success; the app adds the appended comments and merges the doc copy's edits into the doc, each with the comment it comes with.
Any other exit nothing lands but its buddy's "Could not finish." in each thread that asked it; the end of the output is the owner's alone.

A buddy acts only by commenting: an answer, a question or a change to the doc is a comment, and an edit comes with one. It runs when a person's comment asks it, or another buddy's that @mentions it, and its comment in that thread answers it (architecture); its own comment that @mentions another buddy asks that buddy, for a step. A run that posts nothing there answers it all the same, "Looked; nothing to change.", and is not run again for it until someone writes there. The program needs no Ponjo tool: it reads files and edits them.

Paths

The prompt speaks of the project, not of the run: drafts/plan.md is the doc, drafts/plan.md.comments.jsonl its comments, and a path in a comment is from the doc's folder (rule.md is drafts/rule.md). The working folder holds the copies at those paths, so from it the doc's paths are right as they are; any other path is in PONJO_PROJECT. The shipped scripts tell Claude Code (--append-system-prompt) and Codex (its first instructions, before the prompt) so; the Ponjo agent reads the copies or the project by the path alone.

Comments

The sidecar copy holds every thread of the doc (SPEC). To comment, the agent appends lines; the app fills in id, by and at.

Line Makes
{"anchor":{"exact":"…"},"body":"…"} a thread on that text
{"body":"…"} a thread on the whole doc
{"thread":"c_…","body":"…"} a reply in that thread
  • exact quotes the doc copy as the agent left it, as written in the file (markup included), and must be found exactly once (any run of whitespace may stand for another); the app makes the rest of the anchor. Otherwise the thread is on the whole doc.
  • In a thread that asked it, its comments come just after the last comment the run was given, so one written while it worked is still to answer; elsewhere, after the thread's last comment.
  • Only people resolve: a line's resolved is ignored. So is any other change to the copy: changed or removed lines, a thread not in the doc, lines that are not valid.

A buddy comments as a member does. The rules on stdin tell the agent to do what a thread asks of comments; when it asks nothing of them, to comment only where the user has something to decide; and not to repeat in a comment what the app shows: its edits.

Groups

Each comment's edits land as a version of their own, hung on it, so each is undone on its own. An agent says which edits come with which comment in PONJO_GROUPS, a line for each comment with edits, in order: {"comment":<its place among the lines it appended, from 0>,"doc":"<the doc after its edits>"}, the last one's doc the copy as it leaves it. The Ponjo agent writes them. An agent that writes none, or groups that do not end at its copy, lands all its edits with its last comment; with no comment, with the one it left out: the last paragraph it printed, in one line of at most 280 characters, else "Edited the doc.", in the first thread that asked it, or else on the whole doc. No edit lands without a comment.

Wake

A buddy watching the doc runs on every change by another member. An agent that knows what it waits for (its turn, its item) says so in PONJO_WAKE: a line {"line":"<a line of the doc, whole>"} for each line that wakes it. Until its next run, a change wakes it only while the doc holds one of them, such as Action on: Ada. An agent that writes none wakes on any change. The lines are this machine's, kept with the watch in history/<doc>/, gone when the watch is turned off or its run fails; they only make a buddy run less, and an ask runs it whatever they say.

Actions

An agent acts outside the doc only by proposing an action with one of its comments (outside actions). The prompt lists the actions installed here, each with what it does and the input it takes. In PONJO_ACTIONS, a line for each: {"comment":<its comment's place among the lines it appended, from 0>,"action":"<its file name>","input":<JSON>}. An action on a comment that does not land, or not installed here, is dropped. The Ponjo agent gives them with its comment.

An action is a program in actions/ of the config folder (<name>.cmd on Windows) with its manifest <name>.json: { name, about, input }, what it does and what it takes, in words. None ship, and one without a valid manifest is not offered. It runs in a new folder with the input on stdin, as JSON, and its id as PONJO_ACTION_ID, the same if it is carried out again, for a service that drops a second try. Exit 0 is done, and its output's last line the result, posted as its buddy's reply in the thread; any other exit failed.

Agents

An agent is a plugin: a manifest says what can be set, a program does the work. Settings live apart from both, so a program can be replaced (Reset to Default, a new version) without losing them.

In agents/ of the config folder
<name> (<name>.cmd on Windows) the program, under the contract above
<name>.json its manifest: { name, about, settings }; optional
  • The config folder is ~/Library/Application Support/Ponjo/ on macOS. Never in a project: a shared folder must not decide what runs here.
  • Claude Code, Codex and the Ponjo agent ship, written when missing. A newer version replaces one you have not edited (agents/.shipped.json holds the hash of what was written); once edited, it is yours. Reset to Default writes one again.
  • An agent without a manifest is shown by its file name, with no settings.
  • One agent runs every buddy: Settings > Agents lists them, one picked. The picked one shows the fields of its manifest under it, Test (one run on an empty doc, asked only to answer, saying whether it works or what it printed) and for a shipped agent, Reset to Default. To give one buddy another program, branch on PONJO_BUDDY in it.

Settings

settings is an ordered list of fields, as a view's (architecture), with two more types:

type Holds Stored
switch, choice, number as for a view settings.json: agents: { <name>: { <key>: value } }
text a line of text, such as a model the same
secret an API key encrypted with the system keychain (Electron safeStorage), in the config folder; never in settings.json or a log, and shown only by its last 4 characters

A key is lower case letters, digits and _. Only the app's main process can decrypt a secret; it hands the secrets to the doc host, which runs the agents. A manifest that is not valid is ignored, as if there were none. A run gets each field as PONJO_SETTING_<KEY> (model → PONJO_SETTING_MODEL): the stored value or the default, a secret decrypted, empty when there is none. A shell script needs nothing to read them:

#!/bin/sh
exec claude -p "@\"$PONJO_DOC\"" --permission-mode acceptEdits --no-session-persistence \
  --tools Read,Edit,Write,Glob,Grep,WebSearch,WebFetch --strict-mcp-config \
  ${PONJO_SETTING_MODEL:+--model "$PONJO_SETTING_MODEL"} \
  ${PONJO_PROJECT:+--add-dir "$PONJO_PROJECT" --disallowedTools "Edit(/$PONJO_PROJECT/**)" \
    --append-system-prompt "The paths in the prompt are the project's. …"}

@"…" attaches the doc copy to the prompt as already read, so Claude Code edits it without first spending a round trip to read it. The Windows script does not do this yet.

Permissions

Ponjo sets only what the contract needs: the working folder, the copy, and the project folder itself in project mode. The script makes the run unattended and lets it edit the copy. The shipped scripts keep the project read only: an edit there would skip the merge, the receipt and Undo.

What an agent reads can land in a doc teammates read. The Ponjo agent reads only what the project shows to everyone on it (ProjectService: no name starting with ., no link out of the project), and only text files of 20 MB or less: its tools are the boundary (Ponjo agent). Claude Code and Codex read with their own tools, which Ponjo does not limit: Claude Code reads its working folder and the --add-dir it is given, hidden files included, and Codex's workspace-write sandbox reads the whole disk. Running a buddy on them is at the user's own risk, under the CLI's own permissions.

The shipped scripts give an agent no way to act on the outside world: an action there would skip the writer, and could be done twice or by no one's leave (agent runtime). Claude Code gets only its tools to read, edit, search and fetch (--tools), and none of the user's MCP servers (--strict-mcp-config). Codex reads and edits only: it loads no ~/.codex/config.toml (--ignore-user-config), so none of its MCP servers, and no apps or plugins; its sandbox gives its commands no network. A fetch still reaches the web, and can carry out what it read in its URL. What these scripts cannot stop is the CLI's own: Claude Code's hooks in ~/.claude/settings.json, and anything a user adds to a script or its CLI's config, at their own risk.

An agent is not told where the real doc is. If its CLI lets it write there anyway, the app sees an outside change and merges it; a broken sidecar line is skipped, and history keeps every version.

What a prompt hidden in a doc can make an agent do is what its script and its CLI's config allow.

Traces

For whoever works on an agent: with Settings > Agents > Trace runs on (off by default), each run's trace is kept in the config folder's logs/traces/, the newest 200, and read in a doc's runtime panel (the owner's window only). The app records what it sees of any agent: the prompt, the script, stdout and stderr, how it ended, the copies before and after, and what landed. What happens inside the run is the agent's to add: each line it appends to PONJO_TRACE (a JSON value, or text) is kept, in order, as a step. It writes them as it goes, so a run that is stopped or times out keeps the steps it took. The Ponjo agent writes each message of its turn (Ponjo agent); Claude Code and Codex write none yet.

Errors

A run that does not exit 0 changes nothing in the doc. Its buddy answers each thread that asked it "Could not finish.", with Retry, which posts your @<buddy> try again.; the owner sees, in the run's trace, the end of the program's own output, as is, and the script that ran, to run yourself. It runs again only when someone writes in the thread, Retry too, never on its own, so an agent should retry what it can outlast (a busy API) itself.
