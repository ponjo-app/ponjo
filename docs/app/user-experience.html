User Experience

How people and AI buddies write together in Ponjo. For why, see the product vision; for how it is built, see architecture.

Teammates

A project is written by its team at the same time. Everyone on it is the owner (you), a teammate (another person) or an AI buddy, and in a doc they are alike: a face and a unique name, each edits and comments, can be @mentioned, and is named wherever the doc says who did something.

  • Teammates are the friends in the project's room while you host it (Sharing a project). They are trusted: one who can Edit does in a doc whatever you do (edit, comment, resolve, ask AI buddies); one who can only Read sees it all and changes nothing.
  • AI buddies are a name and who it is, in one markdown file. An agent on your computer does their work, when asked. They edit and comment as whoever asked them may; only people resolve.
  • Only you rename, move, delete or create files, and change settings, AI buddies and agents.

The Team button (after the faces) opens the panel: in a project, Open room or, once it is open, the room's link and Lock and Close room; You, the room's teammates, then the AI buddies, ending with New AI buddy (it starts with a random first name, which you can type over: Enter makes it and opens its card). Click a face anywhere for its card: a name that edits in place (yours, or an AI buddy's; a renamed AI buddy keeps its comments, face and color), for an AI buddy who it is, a field right under it saved when you leave it, then Read or Edit for a teammate. A teammate has Kick; an AI buddy has Delete, on its card and its row (its file is deleted). In a doc opened on its own the panel has only you and your AI buddies, and a new one is yours; on a teammate's page, only the owner changes the team and the AI buddies.

The basic loop

  1. Open a doc. Any .md file: File > Open, a double-click in the OS, or a drag onto the app. Each doc gets its own window. The home page opens a project (a folder, or a new one made in the dialog) with its files in a sidebar, and lists the recent ones. A folder with no doc opens with only its files, and New doc and New folder in the page; nothing is made until you ask. A doc opened on its own is a quick editor for you and your AI buddies: no team, no sharing.
  2. Write. Plain markdown, drawn formatted as you type (live preview): the syntax shows only on the lines you are editing. What you see is the file: saving is automatic and changes nothing you did not type, so git diff stays clean. Any other text file (code, config, notes) opens as plain text, and comments and AI buddies work the same there. The Markdown editor is a view (see Views below): switched off, Markdown opens as plain text too. A doc too long to write in smoothly in a view opens in the next one, and says so in a banner: past 1,000,000 characters, Markdown opens as plain text, and the banner offers the Markdown view anyway, warning that typing may lag; past 5,000,000, any doc opens read-only.
  3. Comment. Select text and click the comment button at the page edge (Ctrl+Alt+M). The comment sits in the margin beside its text and follows it as the text changes. A thread not open is folded to its first comment and a line on what followed (who replied, the edits made, a buddy at work, a run that failed); the open one is whole, beside its text, and the others make way. The threads with no place in the text, on the whole doc or whose text was deleted, are one comment icon with their number at the top of the margin, opened in place.
  4. Someone answers. A person replies in the thread. @Clippy in a comment asks the AI buddy Clippy: it replies in the thread, with the edits its reply says why it made, and may comment on other passages. Its reply answers you: it runs again when you write in the thread again. A buddy whose part is to follow your writing (one you chat with as you write, a proofreader) can watch the doc instead: turn on Watch this doc in its card. It looks at once, then each time you pause, and comments where it will, as any member; it wears glasses for as long as it watches, at work or not, and stops only when you turn it off. If you start typing again while it works, it stops and looks again at your next pause. If a run fails, its card says "Watch failed", with why and Retry. Each buddy watching also runs when another buddy changes the doc, so two can play a game there, a long one. Should a doc's buddies run very often (300 runs in 10 minutes; Settings > Agents sets both), its watches pause and the status bar says "Watches paused", with Resume. Why a buddy ran or did not is in Settings > Agents > Agent log.
  5. Anyone allowed decides. Keep an edit, undo it from the comment it came with, reply again, or resolve the thread, whoever asked and whoever answered.

Sharing a project

Sharing is hosting a room, as for an online game. In a project window, Open room in the Team panel gives a link; Copy link copies it. Whoever opens it, in a browser with no install and no account, picks a name once (one already on the project gets a number: Alice2) and is in at once, at Edit, on the project's first doc, with the project's sidebar: the same tree you see, where a click opens any doc in it (another file shows read only; the doc shown stays until the next is drawn) and nothing can be renamed, moved, deleted or made. Which folders are open, and whether the sidebar shows, are kept in their browser.

The panel lists who is in, live. For each you pick Read or Edit, or Kick: their pages close and that browser cannot come back to this room. Lock lets no one new in, once everyone is: those in can still come back after a dropped line. Close room, or closing the project, ends the room at once: every page is cleared and says only "The host closed the room". The next room has a new link; an old one never works again. Nothing about who was in is kept.

A page turned away says why: the room closed, kicked, the room locked, a doc not in the project, a name the project never shares (starting with ., or out of it). A teammate who can only read sees no tool that would be refused: no formatting, no reply box, Resolve, Undo or Restore.

Your computer is the host, so the room is there only while it is awake and the project is open. A teammate whose line drops goes read only at once and says so; what they typed that had not reached you is shown as they left it, to copy, and never sent later. Their page reconnects by itself and, caught up, edits again (after a reload, if it shows such typing).

AI buddies

An AI buddy is a name and who it is, in one markdown file, <Name>.md. The file name is its name; its text, given to its agent as is, says who it is, and the first line shows next to its name.

  • Yours live in buddies/ in your config folder and answer in every doc. The first run makes one, Clippy, a general writing assistant; rename, change or delete it like any other.
  • A project's AI buddies live in its .ponjo/buddies/ and travel with the folder (commit them). They answer only in that project's docs, and win over one of yours with the same name.
  • A doc opened on its own (from Finder, say) reaches only yours, even if it sits inside a project folder.
  • Each has its own face and color, the same on every machine with the same AI buddies: up to eight in a doc get eight colors.

Editing the files by hand works too: the app picks up changes at once. What runs every AI buddy is the agent picked in Settings > Agents (Claude Code, Codex, or the Ponjo agent, which runs a cloud model you pick): a program in agents/ in your config folder that you may edit (see agent config). The one picked shows its settings there, under it (a model, an API key), kept apart from its program; an API key shows only its last 4 characters. Test runs it once and says whether it works, or what went wrong. Settings > Usage shows what the Ponjo agent's runs used of the Claude API: runs, input and output tokens, the share read from the prompt cache and an estimate of the cost, for today and the last 7 and 30 days, and by model.

Who asks whom

  • @name in a comment asks that AI buddy.
  • A reply with no @ asks the AI buddies already in its thread: a first comment on a passage and the replies under it.
  • A comment asks until the AI buddy replies in its thread: it runs once, answers, and runs again only when someone writes there again, never on its own, on an edit or on a clock. Resolving the thread, which only people do, stops a buddy working on it at once, and nothing it did there lands. Reopening asks no one.
  • Work starts with people's comments: yours, and a teammate's who can edit. A turn acts as whoever asked it may when it ends: if they were removed or set to Read meanwhile, nothing it did lands. An AI buddy's reply asks only an AI buddy it @mentions, for that same person; an @name typed in the doc's text asks no one.
  • A comment that reached the file from outside Ponjo (a git pull, another editor, another computer) asks no one.
  • A comment that mentions several AI buddies asks each; they work at once. Each works on every thread that asks it in one run, one run at a time.
  • Every run starts fresh with the doc, who the AI buddy is, who is in the doc and the threads that ask it. Nothing is remembered in private; anything worth keeping is written in the doc or the threads.

Everyone edits, and every edit can be undone

  • A person's typing lands in the doc as they type. An AI buddy edits a copy of the doc; when it is done, its changes are merged into the doc as it is then, at once, and glow for a moment with its name, as anyone's do.
  • An AI buddy comments as people do: on any passage, or in any thread. It never resolves. Its comments ask no one.
  • No edit without a comment. Every edit an AI buddy makes comes with a comment, its own reply or one the app posts for it, empty, when its agent said nothing. Under that comment the app shows how many places it edited; clicking it shows them in the text as a revision (and scrolls to them): new text in its color, removed text grey and struck through where it was, until you type, press Escape or click it again. Edits changed since are left out. The comment only says why, or what you need to decide.
  • Nothing a person types is lost. When two people change the same place at once, both edits stay, in the order they reached the host. Text one deletes while the other types inside it keeps what was typed. If both replace the same word, both new words stay, to fix by hand.
  • A person's typing is trusted. It is not marked by who typed it, and when two people disagree they settle it outside the app, in a call.
  • People win over AI buddies. Where a person changed the same lines while an AI buddy worked, the person's lines stay, the rest of its change lands, and its comment says part of it was not applied: ask it again to redo it. A change from outside merges the same way.
  • Undo is one thing, for your typing, an AI buddy's run, a teammate's change or one from outside: it takes those edits back, all at once, and keeps everything written since; where someone changed those lines since, their lines stay. Cmd+Z (Ctrl+Z) undoes your own typing, never anyone else's. Undo on an AI buddy's comment undoes the edits it came with, and no other comment's; the comment stays; Redo there puts them back, by undoing that undo. Undo this change in history undoes any version, or a burst of typing. It works in every window of the team.
  • A failed run changes nothing in the doc: in each thread that asked it, the buddy replies "Could not finish." in red, with Retry, which asks it again as you ("@Clippy try again."). Only you see why (the end of its output), in the run's trace. It runs again only when someone writes in the thread. A buddy that found nothing to do says so: "Looked; nothing to change."
  • Actions outside the doc. An AI buddy acts outside the doc (posts a message, opens an issue) only by proposing an action with its comment, never by itself. The action shows under that comment: what it is, its input in full, and that it waits. You, and only you, Approve or Decline it: it runs on your computer, with your keys, once. Then it says who approved it and when, and its result is the buddy's reply in the thread. One that failed, or that was running when Ponjo stopped and may have run, shows in red with Retry; it never runs again on its own. Undo on the comment takes back its edits, never its actions. Settings > Actions lists the actions installed on this computer (none come with Ponjo), each with Ask first, on by default; off, that action runs at once, and only for what you asked.

Seeing teammates work

  • Presence. People's avatars are circles in a hat: the owner's a crown, a teammate's a top hat. Each AI buddy's is a soft blob with a face. The header has one queue of them, every face alike (point at it for its name card, click for its card), then yours, then Team. It is ordered by what each is doing: who is working first (an AI buddy running, a person who moved or typed in the last few seconds), then who is here, then who is away (a person on another doc, or for the owner a teammate not in the project); a face moves only when its state changes. A face shows its state wherever it appears, the same for everyone: while working it grows, its body rolls and its eyes turn focused; where an AI buddy cannot answer or a person is away it is greyed out; and when a run fails it shakes and flashes red once. No dots or badges. In the Team panel you see which teammates are here; a teammate sees who is here with them.
  • Cursor. Every teammate at work in the doc has one cursor, a blinking line in their color with no name: a person's while they move or type and a few seconds after, where they are typing; an AI buddy's while its run goes, at the passage it was last asked about or the end of its last edit. A cursor follows the text as it changes, and is hidden where its text is gone. It is only drawn: never in the file, and it takes no clicks.

Around the doc

  • Find and replace (Ctrl+F; Ctrl+Alt+F with Replace), in every view and in history: what a reader sees, every match marked, Enter for the next. It finds what is typed, case ignored; Aa matches case, ab whole words, .* a regular expression (then $1 in Replace is its first group). The three are one choice for every find bar and the sidebar's search. Replacing is your own edit, undone with Ctrl+Z.
  • Print and Export as PDF (File menu): the doc as a reader sees it, light, without the app around it, its comments or anyone's marks.
  • Version history (clock button, Ctrl+Alt+Shift+H): every version with who made it (you, a teammate, both when you typed together, an AI buddy with the comment it answered, or a program outside Ponjo), a diff against the one before, Undo this change and Restore. A version is saved each time typing pauses (a burst of typing shows as one), before and after each buddy edit, before each change from outside Ponjo, and for each undo and restore, so any of them can be undone or restored. History is kept in the config folder, never next to the doc.
  • Changes from outside (a git pull, another editor) show up live and merge with your typing, line by line. Where they changed a line you changed too, your line stays and their version is in history.
  • Settings (name and theme, views, shortcuts, agent) are the same dialog in every window, the home page too (it has no Views: those come with a doc), and a change applies at once to all of them. How a doc looks and what its editor offers are its view's settings, not global ones. Buddies are not in Settings: they are changed on their cards.
  • Views. A doc has a view, its editor, switched on or off in Settings > Views (it lists the views with their files, what they do and whether they are on; a view's page has its switch and its own settings). Every text file opens in the Plain text view (always on) unless a view gives its format an editor of its own; the built-in one is for Markdown and on by default. How changes merge is the same in every view. The Markdown view (design) is live preview: the file's own text drawn formatted, its syntax shown only where it is being edited: a span's while the selection touches it, a block's markers in the margin. All of CommonMark and GFM, and footnotes, are drawn (#358). Typed Markdown formats as it is typed; the toolbar types it too, and so do the standard keys (Mod+B, Mod+I, Mod+E, Mod+Shift+X, Mod+K, and Mod+Alt+0–3, Mod+Alt+Q, Mod+Alt+C, Mod+Shift+7–9 for the block styles). Its toolbar, outline and focus mode (Ctrl+Shift+.) are part of it. Pasted formatted text is turned into Markdown as it is pasted; plain text goes in as it is. To see the whole file as source, switch the view off (Ctrl+Shift+T, again to switch back); .md then opens in the plain editor. The plain editor's settings: line numbers, wrapping, font size, whitespace marks (in the selection, everywhere or off) and indent guides, and indentation: Tab types the file's indent (found from the file, or tabs or spaces as set), Tab and Shift+Tab (or Mod+] and Mod+[) indent and outdent selected lines, and Enter keeps the line's indent. In a code file Mod+/ comments out the lines and back, Alt+↑ and Alt+↓ move them, Mod+Shift+K deletes them (elsewhere Mod+/ shows the shortcuts). While comments show, a hairline on its right edge is where its text ends. It has a status bar with the caret's line and column, the size of the selection, the indent Tab types (a menu of others, for what you type next, never the file) and Wrap and Whitespace toggles that change the same settings. The Markdown view's: the page's font and width, Outline and Focus mode. Every doc has a status bar under the page: in the Markdown view the doc's word count (of the selection too, when there is one), and which buddies are working while their turns run. Switching a view applies at once to every open doc: a Markdown doc turns to plain text and back, comments still in the margin, and nothing is written.
  • Files. New Doc and Rename (the comments move too). Opening an already open doc focuses its window. If the file is moved or deleted outside the app, a banner says so and saving pauses.
  • A project's sidebar shows every file and folder as it is on disk, except names starting with . and comment files, each folder read as you open it. What git ignores (build output, installed packages) is dimmed. Mod+P finds a file by its path in the sidebar's filter (a regular expression): the matches show in their folders, those git ignores dimmed and last (not inside a folder it ignores), and Enter opens the first. Ctrl+Shift+F (or the button before the field) turns the field to search the files' text, as the find bar finds: each file it is in, then each line with its number, the match marked; what git ignores is not searched, and past 1,000 matches it says so. A line opens its file with the find bar at that match. Everyone on the team sees the same tree. A doc opens in the editor; any other file shows read only in its place, an image as the image, up to 5 MB (Escape goes back). A file's path in a comment, as Copy Path writes it, is a link that opens it; in the link popover, typing finds the project's files and links one by its path from the doc. Its menu, the same for every row and only yours: New File and New Folder (in a folder; / in a name makes folders), Rename (F2), Copy Path (relative to the project, as AI buddies read it), Reveal, and Delete (to the Trash). Drag a row onto a folder to move it. A file's comments go with it when it is renamed, moved or deleted here.
  • Comments are in X.md.comments.jsonl next to the doc, one per line, so they merge in git (format). Moving a doc outside the app, move this file with it.
