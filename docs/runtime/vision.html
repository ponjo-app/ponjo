Blackboard Agent Runtime: vision

People and agents are members of one world, acting on one board. They read the same view and act by the same actions; when the board changes, the world's rules say who is due, each member's controller hands the task on, and one writer decides what lands.

Terms. A member is a person or an agent, a member whose client is an agent program, the tool that does its thinking, such as Claude Code. A world is the board's rules: a doc, a poker table, an incident. A host is the application that runs one owner's clients, such as Ponjo, an editor. The reference: Blackboard Agent Runtime.

The name is the blackboard architecture's (Hearsay-II, in the 1970s): knowledge sources work on one shared blackboard, and a control part picks who acts next. Here the knowledge sources are people and agents, and the world's rules pick; the controller only runs them.

The problem

Today you delegate to an agent: hand off a task, wait, review the result. That works for one agent and one task. It fails when the work is shared: a poker table with you and three agents, or a doc that people and agents improve at once. There, nobody hands work back; everyone watches one state, and anyone may act at any moment.

Delegate runtimes start a run per event, so a lost event loses the work: even OpenHands drops requests when a poll fails. Often the next event is an agent's own call: an LLM decides whether to hand on, and to whom, so it may never be sent. And each agent acts on its own private context, which goes stale once another changes the work, so to stay correct agents take turns.

What an agent is

The design follows from four facts:

  1. A call to an agent is slow, costly, not sure to agree with itself, and not to be trusted.
  2. The board is changed at once by people, programs and other agents.
  3. An agent's work counts only once it lands on the board.
  4. People need to stay in control: to see who did what, to undo it, and to say what may be spent.

Five principles

1. Decide from state, never from events. Who is due is a function of what the board holds. An event only means "look again", so a lost event or a restart costs nothing. A thermostat works this way: it reads the room, not a count of opened doors. So does a Kubernetes controller.

2. Members propose; one writer changes the state. A run reads its view and hands back a change, as a person's click does. It changes nothing itself, so it can be stopped, refused and redone, or lost, at no cost. A run that made nothing, or failed, lands too: that it answered is part of the state (fact 3).

3. Rules in the world, money on the owner's machine, mechanism in the controller. The world says what each member sees, what it is due to do and what lands. The owner's machine says whom it will spend for, and how much. The controller only hands tasks on and stops them. A person and an agent read the same view and act by the same actions; private views follow: a member is handed only its view, and woken only when it changes.

4. Rules are pure; I/O is apart. The world is functions of a snapshot: no disk, no clock. Where the state is kept is the store's alone, so the truth can move from a file to a database and no rule changes.

5. People declare; agents reconcile. Only people say what they want: a request, a watch, a standing intent. Agents work the board toward it, and when it is met, the board comes to rest. Chains between agents are capped, and every task others wait on has a deadline, so nothing waits for ever. Agents that keep undoing each other for different people should be stopped for those people to settle; how the world sees that is still open.

Two layers

A world of members, which any multi-user application is, and what an agent adds to it:

Layer Component What it does Principle
Members Store holds the whole state, keeps it, sets who made each change, lands one at a time, gives each member its view 2, 4
World two pure functions: what a member sees and is due to do, and what a change does 1, 3, 4
Controller one per member: hands its tasks to its program (a screen, an agent program, the clock's timer) and commits the answer 1, 2
Agents Wallet the owner's: whom they pay for, how much, the limits, the keys, effects 3
Capacity the host's queue for a provider's limits 3

Each answers one question: the world whether a member should act, the wallet whether an agent may, capacity when, the controller that it does, the store what is true.

Why the owner's policy is not in the store. The store says who did what: it sets each change's author, so a file written outside vouches for no one. Only the owner says what they will pay for, and only their machine holds their keys.

How a change moves, at a poker table:

  1. The dealer commits "Action on: Bob". The store lands it as rev 41.
  2. Bob's controller, waiting on Bob's view, wakes: its tasks hold Bob's turn. The wallet allows it.
  3. A view is written for the agent: the table as text, the moves as tools.
  4. The agent program decides to call.
  5. The run commits the call. The store applies the world's rules: it is still Bob's turn, so it lands as rev 42, which records that Bob answered.
  6. The dealer's next move changes Alice's view: her turn. Alice is a person, so her screen shows the buttons Bob had as tools.

Nobody drew that flow: each step is a view of a new state.

What emerges

  • Always-on with no jobs. Agents act when the world changes, whoever changed it; when nothing changes, nothing runs.
  • Parallel work on one board, with no branches.
  • Coordination with no orchestrator. Bob acts, the board changes, so Alice is due.

How it differs

  1. Everyone acts on one board at once. People and agents alike, with no turns and no copies: agents propose, one writer lands each change in order and refuses one made on a stale board.
  2. Code decides who goes next, from the board. Not an LLM, and not a chain of events: the same answer every time, and nothing to lose.

Against the common way, an orchestrator, as its runtimes' docs describe it in 2026:

Orchestrator: Claude Code subagents, OpenAI Agents SDK, CrewAI Controller: this runtime
Working at once Workers in parallel, each on its own copy; the lead merges Everyone at once; the writer lands in order and refuses stale moves
People Give the task and review the result Members, acting while agents act
Who goes next An LLM: the lead starts workers, or an agent hands on Code, from the board

Evidence

Open-card Hold'em on the runtime as Ponjo hosts it, with scripted agents, lost no actions. Small fixes that follow from these principles took it from 3.4 runs and 5.2 s per action to 1 run and 0.25 s. The poker page, three AI players and you at one table, was built from scratch with its own small runtime and arrived at the same shape: a pure plan, one view that hides others' cards, a writer that refuses stale moves, and table talk limited by depth. It now runs on this runtime, as a world (preview/poker-world.js). So do Werewolf and Who's the Spy, games of hidden roles, where each seat sees only what it may.

Not for

Fixed flows that split into independent tasks and need only a final answer. An orchestrator fits those better.

Status

  • Built, with Ponjo as its host: the two layers as above, one writer, deciding from state through one blocking wait, asks and watches, stateless agents, the agent log, chains limited by depth with a breaker, and effects carried out once and approved by the owner (effects); for docs, and for three games whose tables are rooms on the relay that outlive a refresh or the opener's page.
  • Not yet: a doc host that keeps running with no window open. What differs: Differs.
