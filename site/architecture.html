How Ponjo is built

People and AI buddies edit the same file at once. One host on your machine orders every edit, no one resolves a conflict by hand, and our own agent proposes edits the program checks.

    Merge strategy

    An edit merges by how it comes, not by who made it. Typing and pasting merge by character. A whole text that arrives late (a buddy's turn, an outside change, an undo) merges by line: where both changed a line, the doc as it is wins.

    Type in both. Each edit goes to the host on the revision it was made on; one made on an older revision is moved over what landed since. Nothing typed is dropped, and both pages end on the file's text.

      The Ponjo agent

      Our own agent, for only what co-writing needs: read, comment, edit. The model reads and proposes; the program checks and applies. Its loop, turn(), is one file that imports nothing, so this page runs it too.

      Promptthe thread and the rules, the doc with line numbers, the project's file names
      inferone step of the model: Anthropic, OpenAI-compatible or Nebius
      Toolsreadfindgrepcommentresolveproposeresults go back to infer, until propose ends the turn; at most 20 steps
      The tools are the permissionsNo shell, and no network but the model's API. It reads only its copies and the project's visible files, so text in a doc can at worst make an undoable proposal.
      Read by line number, write by quotepropose edits as { old, new }, each old found in the doc exactly once, or the whole proposal goes back to fix. It never counts characters.
      StatelessA turn remembers nothing after. Its messages are its state, and its trace replays it. It lands as any turn does: its copy merged by line, as above.
