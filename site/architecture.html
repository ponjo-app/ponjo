Ponjo Agent Runtime Design

In Ponjo, many people and AI agents write one doc at the same time, and you stay in control. It works because of one design choice: an agent’s context lives in the doc, not in a hidden chat session. So agents can work in parallel, you can see everything they know, and everyone works from the same context.

The problem

Context lives in a chat session

In tools like Claude Docs, as we used it, an agent works in a chat session behind the doc, and its context builds up there, on top of the doc.

Asks wait in line. Each run builds on what the session kept from the last one, so a new ask in the same session waits for the one before it to finish.
What the agent knows is hidden. Its context is a history you never see, so an edit can rest on things that were never on the page.
Context splits. What one person’s session learns stays in that session, so the people and agents on a doc each work from a different picture.

The solution

Context lives in the doc

In Ponjo, each agent run is a stateless function of the doc, its comments, and the thread it answers.

Ask many things at once. A run starts from the doc and its thread, never from what an earlier run left behind. Runs in different threads, or by different agents, go in parallel: ask for a rewrite in one thread and a fact-check in another, and neither waits.
Nothing it knows is hidden. A run knows only the doc, its comments, its agent’s persona, and the files it reads, all of which you can see. Turn on traces to see exactly which ones it read.
Everyone shares one context. Every agent reads the same doc, comments, and files. What an agent learns goes into the doc or a comment, where teammates and their agents pick it up.

How it works

One writer, and a stateless run per ask

  1. Ask many things at once. An ask is a comment. The runner keeps one run going for each open ask, each on a fresh copy of the doc and its comments. No run depends on another, so there is no queue, and any run can stop or start over.
  2. Nothing it knows is hidden. A run gets the doc, its comments and its buddy’s persona, and can read the project’s files, read only. It keeps no memory between runs; with traces on, each run lists what it read.
  3. Everyone shares one context. One doc, one set of comments, one project, read by every run whoever asked. What a run learns comes back only through the doc, as an edit or a comment.
  4. You stay in control. The doc host is the only writer of the file. It merges each run’s copy into the doc as it is now, line by line (merge3); where you changed the same lines, yours stay and the run redoes its edit on them. Each run lands as one version you can undo.
